## 🎯 Objetivo

Ao final da atividade, o aluno será capaz de:

1. Responder a **20 questões** de prova em 60 minutos, com leitura atenta.
2. Conferir o próprio desempenho contra o **gabarito comentado** e entender **por que** errou.
3. Fazer a **autoavaliação** por competência e montar um **plano de estudo** para a próxima
   etapa.

**Objetivo secundário:** transformar a nota em **plano de ação** — o que fazer na semana
seguinte com base no resultado, e não só um número.

## ✏️ Como usar este material

1. Peça ao aluno para **cronometrar 60 minutos** e responder **sem consultar** o material.
2. O aluno marca as respostas na **folha de gabarito** do final deste arquivo.
3. Só depois: abra o **gabarito comentado** e compare. Corrija **no papel**, com a caneta
   vermelha — marcar é o que fixa.
4. Classifique cada erro como **erro de leitura** ou **erro de conteúdo** (veja a tabela de
   autoavaliação).
5. Monte o **plano de ação**: quais bancos de exercícios revisar.

## ✅ Gabarito comentado — Simulado 02

| # | Resposta | Comentário |
|---|---|---|
| 1 | **C** | `GET` **consulta**; `POST` cria; `PUT` substitui; `DELETE` apaga. Um `GET` que altera dados quebra a regra do HTTP e o cache dos navegadores. |
| 2 | **B** | `201 Created` = recurso criado. `202 Accepted` seria "aceito, ainda processando". |
| 3 | **B** | `application/json` é o padrão para JSON. `multipart/form-data` é para envio de **arquivos** em formulário. |
| 4 | **C** | `401 Unauthorized` = sem credencial válida. `403 Forbidden` = credencial válida, mas sem permissão. `500` é erro do servidor. |
| 5 | **A** | Lista em JSON é entre **colchetes** `[ ]`; objeto é entre **chaves** `{ }`. Em JSON, chave repetida no mesmo objeto é inválido — por isso a B está errada. |
| 6 | **V** | Sem `try/catch`, a `Promise` fica **rejeitada** e o `catch` nunca roda: o texto "Carregando..." fica lá para sempre. |
| 7 | **B** | `GET` lê; `POST` cria ou envia. `GET` **não deve** alterar dados — é o que permite cache e compartilhamento de link. |
| 8 | **B** | `SELECT nome FROM aluno;` — o `*` traria **todas** as colunas. |
| 9 | **B** | `GROUP BY` junta linhas com o mesmo valor. `HAVING` filtra **depois** de agrupar; `WHERE` filtra **antes**. |
| 10 | **A** | `WHERE` age na linha original da tabela. `HAVING` age no grupo já formado. |
| 11 | **B** | `COUNT(*)` conta linhas. `COUNT(coluna)` só conta as linhas em que a coluna **não** é `NULL`. |
| 12 | **B** | Relação **N:N** (muitos para muitos) sempre vira tabela intermediária, que carrega os dois ids. Isso é **normalização**. |
| 13 | **B** | `LEFT JOIN` **preserva** a tabela da esquerda (traga a Elisa, que não tem matrícula). `INNER JOIN` só devolve quem tem par nos dois lados. |
| 14 | **C** | `UNIQUE` não deixa repetir. `NOT NULL` impede vazio. `CHECK` valida um intervalo. `PRIMARY KEY` garante a unicidade da chave — mas o e-mail não é a chave. |
| 15 | **V** | Por isso o `WHERE` é obrigatório na prática. Sem ele, o `UPDATE` altera a tabela inteira. |
| 16 | **B** | É a tentativa de **encaixar código SQL** no texto digitado. A defesa é usar **consultas parametrizadas** (`?`), nunca concatenar texto na consulta. |
| 17 | **B** | O código injetado roda no navegador de quem abre a página. A defesa é **escapar/sanitizar** a saída e usar CSP. |
| 18 | **B** | Rede aberta é rede **compartilhada**. Dados de pagamento exigem HTTPS e, de preferência, VPN. |
| 19 | **V** | Dado pessoal é todo dado que identifica uma pessoa. Compartilhar sem necessidade viola a **LGPD** (Lei nº 13.709/2018). |
