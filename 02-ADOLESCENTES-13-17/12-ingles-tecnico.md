# B12 — Inglês Técnico (13–17 anos)

**Duração:** 90 min · **Aula 12 de 16**

---

## 🎯 Objetivo

Ao final da aula, o aluno será capaz de:

1. Explicar **por que o inglês aparece no trabalho**: documentação, mensagens de commit, issues, pull requests, nomes no código e mensagens de erro.
2. Reconhecer e usar **60 a 80 termos essenciais** de inglês técnico com a tradução e uma frase de uso real.
3. Escrever **mensagens de commit** e **issues** com estrutura profissional.
4. Escrever o **README do projeto em inglês** com as seções corretas e exemplos que funcionam.
5. **Ler** um README real em inglês e extrair dele o que precisa (seções, requisitos, comandos).

**Objetivo secundário:** Ser honesto sobre o nível. **Esta aula não é de gramática.** O objetivo é **ler e escrever o suficiente para trabalhar** — e saber dizer, com clareza, o que você já consegue ler e o que ainda precisa de tradutor.

## 🧠 Conceitos-chave

| Conceito | Frase que fixa |
|---|---|
| **Documentation** | "O código diz o que faz. A documentação diz **por que**." |
| **Commit message** | "É uma carta para quem vai ler o histórico daqui a seis meses." |
| **Issue** | "Um bilhete que explica o que precisa ser feito (ou consertado)." |
| **Pull request** | "Um pedido de entrada, com a explicação do que muda." |
| **Code review** | "Alguém lê o seu código **antes** de ele entrar. Crítica construtiva." |
| **LGTM** | "Looks good to me. Aprovado." |
| **README** | "A porta de entrada do repositório. Em inglês, porque o mundo lê em inglês." |
| **Imperative mood** | "Commit no imperativo: `add`, não `added`." |
| **Conventional Commits** | "`feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:` — o prefixo conta a história." |
| **Happy path** | "O caminho que dá certo. Teste ele primeiro." |
| **Edge case** | "O canto estranho: campo vazio, acento, número gigante." |
| **Deprecated** | "Aviso: isto vai sumir. Não use." |
| **Environment variable** | "A configuração que fica **fora** do código." |
| **Secret / token** | "Chave de acesso. **Nunca** vai para o Git." |
| **Dependency** | "Biblioteca de terceiros que o seu projeto usa." |
| **License** | "As regras do que você pode fazer com o código." |
| **Contributing** | "O README que diz como contribuir. É o convite." |
| **Badge** | "Imagem que mostra status do build, do teste, da cobertura." |
| **Structure** | "Inglês técnico é mais **estrutura** do que gramática." |

## ⏱️ Roteiro (90 min)

### Fase 1 — Apresentação (10 min)

**Gancho:** *"Você já leu mensagens de erro em inglês a vida inteira: `Cannot read
property of undefined`, `Permission denied`, `Connection refused`, `ModuleNotFoundError`.
Elas não vêm da sua escola — vêm de bibliotecas publicadas por pessoas que nunca vão
te conhecer. O inglês do computador é a língua do mundo, e a sua turma vai publicar
código open source nele."*

**Demonstração ao vivo (5 min):** abra um repositório real no GitHub e mostre quatro
lugares, um de cada vez:

1. A aba **Issues** — uma issue escrita em inglês
   ([documentação](https://docs.github.com/pt/issues)).
2. O **README** em inglês de `ingles-para-programadores/README.md` — badges, tabela
   de índice, seções de uso, contribuição e licença.
3. A aba **Commits** — mensagens com prefixo: `feat:`, `fix:`, `docs:`.
4. Um **código de erro real** no terminal (rode `python arquivo_que_nao_existe.py`).

Diga: *"Nenhum desses quatro lugares exige inglês perfeito. Exige **estrutura**."*

### Fase 2 — Exploração (20 min)

**Parte 1 — Por que o inglês aparece no trabalho (5 min).**

O repositório abre a aula com essa discussão em
`ingles-para-programadores/01_fundamentos/exercicio_02_por_que_ingles.txt`, que traz
5 situações reais e uma tarefa prática: pesquisar *"how to center a div CSS"* no
Google em inglês e anotar de onde veio o primeiro resultado.

| Onde o inglês aparece | Por quê |
|---|---|
| **Documentação** | a documentação oficial de Python, React, Node e Linux está em inglês |
| **Mensagens de commit** | o histórico de qualquer projeto open source é em inglês |
| **Issues e pull requests** | é o canal de comunicação com desconhecidos do outro lado do mundo |
| **Código** (nomes de função, variáveis, mensagens) | o vocabulário técnico é em inglês: `render`, `fetch`, `parse`, `save` |
| **Mensagens de erro da biblioteca** | `TypeError`, `KeyError`, `ModuleNotFoundError` — você precisa saber ler essas palavras |

Do mesmo arquivo, o gabarito do "verdadeiro ou mito" diz que **programadores
brasileiros precisam de inglês** para crescer na carreira — e que **a maioria dos
bugs são de lógica, não de inglês**. Diga: *"Ninguém vai reprovar você por escrever
`add user` em vez de `adicionar usuário`. Mas ninguém vai ler seu `adicionar usuário`
também."*

**Parte 3 — Honestidade sobre o nível (3 min).**

Diga e escreva no quadro:

```
Isto NÃO é aula de gramática.

Não vamos estudar present perfect, nem voz passiva, nem
"which" contra "that".

Vamos aprender:
  1. 77 palavras que você vai ler toda semana;
  2. 6 formatos (commit, issue, PR, README, comment, descrição);
  3. 10 frases-modelo prontas para copiar e adaptar.
```

Explique os erros que mais importam no trabalho: ordem das palavras, `a`/`an`,
`do`/`does`, `will`/`going to` — e que **erro de inglês em commit não quebra nada**;
erro de inglês em **documentação** quebra o projeto. Diga: *"Inglês técnico é
**estrutura**, não gramática. Quem escreve bem um README em inglês com 300 palavras

### Fase 3 — Mão na massa (35 min)

**Atividade A — Flashcards: o dicionário de bolso da equipe (10 min).**

Cada aluno sorteia **12 termos** da tabela acima e monta um flashcard:
frente = termo em inglês; verso = tradução + **1 frase real de uso** (do jeito que
apareceria num commit, issue ou README).

Podem montar no papel ou usar
`laboratorio-tech-social/site/exercicios/flashcards.html`.

Regra: a frase do verso **não pode ser uma tradução literal**. Tem que ser uma frase
que você poderia usar de verdade. Exemplo ruim: *"Commit = commit"* (inútil).
Exemplo bom: *"Commit your changes before the end of the day."*

**Atividade B — Frases-modelo: commit e issue (10 min).**

**Commit** — o padrão do repositório
(`ingles-para-programadores/04_vocabulario_git/exercicio_03_mensagens_commit.txt`):

| Prefixo | Quando usar | Exemplo real do repositório |
|---|---|---|
| `feat:` | nova funcionalidade | `feat: add login function` |
| `fix:` | correção de bug | `fix: fix form submission bug` |
| `docs:` | alteração em documentação | `docs: update README with setup instructions` |
| `style:` | formatação (não afeta a lógica) | `style: fix indentation in app.js` |
| `refactor:` | refatoração (não muda o comportamento) | `refactor: rewrite validation function` |
| `test:` | adição ou correção de testes | `test: add tests for Login component` |
| `chore:` | manutenção | `chore: update dependencies` |

As 5 regras de ouro (de
`ingles-para-programadores/11_escrita_tecnica/exercicio_04_commits.txt`):
1. **Modo imperativo**: "Add feature", não "Added feature".
2. **Curto**: uma linha, menos de 72 caracteres.
3. **Uma preocupação por commit**.
4. **Explique o porquê** quando não for óbvio.
5. **Prefixe sempre**.

Ruim: `fixed stuff`, `update`, `asdfgh`, `done lol`.
Bom: `fix: resolve memory leak in data processing`.

**Issue** — o formato do repositório
(`ingles-para-programadores/09_frases_comuns/exercicio_03_issues.txt`):

```
Title: [breve descrição do bug]

## Description
## Steps to Reproduce
1.
2.
3.
## Expected Behavior
## Actual Behavior
## Environment
- OS:
- Browser:
- Version:
## Additional Context
```

E, para **feature request**:
```
## Feature Request
## Problem
## Proposed Solution
## Alternative Solutions
## Use Cases
```

Cada aluno escreve **1 issue real** sobre o projeto da turma (pode ser um bug
encontrado na aula 08 ou um recurso que falta).

**Atividade C — Leitura de um README real em inglês (15 min).**

Abra `ingles-para-programadores/README.md` e `o-despertar-qa/README.md`. Em dupla:

1. **Ache as seções** em cada README: título, descrição, badges, instalação, uso,
   contribuição, licença. Marque no papel onde cada uma está.
2. **Extraia 10 palavras técnicas** do texto e escreva a tradução — é o mesmo
   exercício de `ingles-para-programadores/14_projeto_ler_docs/exercicio_01_python_tutorial.txt`,
   que usa um trecho real da documentação do Python.
3. **Recicle 1 frase-modelo** que você vai usar no README do seu projeto.
4. **Teste**: você conseguiria instalar o projeto de `o-despertar-qa/README.md` só
   lendo? O que falta? (falta a seção de licença e de contribuição — sua equipe
   pode fazer melhor).

### Fase 4 — Projeto (20 min)

**Desafio: "README do projeto em inglês"**

Escreva o `README.md` do **projeto final** em inglês, com esta estrutura:

| Seção | O que vai dentro |
|---|---|
| **Title** | nome do projeto |
| **Badges** | status do build, do teste, da cobertura (opcional, mas bonito) |
| **Description** | o que o projeto faz, em 1 ou 2 frases |
| **Requirements / Prerequisites** | Python 3.10+, navegador, o que mais for preciso |
| **Installation** | comandos copiáveis, em bloco `bash` |
| **Usage** | 1 exemplo de uso + a saída esperada |
| **Screenshots** | imagem do projeto (opcional) |
| **Contributing** | como contribuir (link para o `CONTRIBUTING.md`) |
| **License** | tipo de licença + link |

**Critério de pronto:**
- [ ] README **inteiramente em inglês** (só nomes de arquivo e nome da licença ficam como são)
- [ ] As **9 seções** presentes — nenhuma em branco
- [ ] **Installation** com comandos copiáveis que **funcionam de verdade** (teste em uma máquina limpa)
- [ ] **Usage** com 1 exemplo de código **e a saída esperada**
- [ ] Todos os commits do projeto em inglês, com prefixo do Conventional Commits
- [ ] **1 issue real** aberta no repositório da turma, em inglês, no formato do repositório
- [ ] Licença nomeada (MIT, Apache-2.0 etc.) + arquivo `LICENSE` no repositório
- [ ] Commit com `docs: add English README to the project`

### Fase 5 — Mostra (5 min)

## 📝 Avaliação

| Instrumento | Critério |
|---|---|
| README em inglês | 9 seções + exemplos que rodam de verdade |
| Vocabulário | 12 flashcards por aluno, cada um com frase real de uso |
| Commit | Em inglês, imperativo, com prefixo, com menos de 72 caracteres |
| Issue | Formato completo do repositório (steps to reproduce, expected, actual, environment) |
| Leitura | Extraiu as seções e 10 termos de um README real |
| Honestidade | Aluno sabe que a aula não é de gramática e diz o que já lê e escreve sozinho |
| Pergunta de saída | "What is the difference between 'fix' and 'refactor' in a commit message?" |

**Pergunta de escrita:**
> "Você abriu uma issue no GitHub porque o botão de download não funciona no Safari.
> Escreva a issue **em inglês**, usando o formato do repositório: título, descrição,
> passos para reproduzir, comportamento esperado, comportamento atual e ambiente."
> **Resposta (modelo, no formato de
> `ingles-para-programadores/09_frases_comuns/exercicio_03_issues.txt`):**
>
> ```text
> Download button doesn't work on Safari
>
> ## Description
> When I click the download button, nothing happens.
>
> ## Steps to Reproduce
> 1. Go to the products page
> 2. Click the download button
> 3. Wait for the download to start
>
> ## Expected Behavior
> The file should start downloading.
>
> ## Actual Behavior
> Nothing happens.
>
> ## Environment
> - OS: macOS Ventura
> - Browser: Safari 17
> - Version: v2.1.0
> ```
>
> Repare no que importa: **o título diz o que quebra e onde**; "Expected" e "Actual"
> são frases diferentes (é essa diferença que o revisor vai usar); e o bloco
> "Environment" existe para que alguém com Mac e Safari consiga reproduzir o erro.
> Uma issue bem escrita economiza horas de quem vai arrumar.
